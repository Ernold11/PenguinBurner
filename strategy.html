PenguinBurner · in-game overlay

Steam-Grade Overlay

The overlay works and nobody would call it good-looking. It draws one line of 5×7 all-caps pixels on an opaque black bar, welded to the top-right corner. Here is what it actually does today, what “like Steam” can realistically mean for a tool that also drives Lutris and Heroic, and a four-stage route from one to the other.

Renderer
vkCmdClearAttachments only. Every glyph row is a cleared rectangle. No pipeline, no shaders, no textures, no vertex buffers.
Consequence
No alpha. A cleared rect writes its colour straight in, so the backing box is hard black and the text is hard white. Translucency is not a setting we forgot — it is unreachable from here.
Font
45 glyphs, 5×7 pixels. A-Z, 0-9 and + - / % . Everything is passed through toupper, so there is no lowercase and no colon.
Live mismatch
The Overlay tab previews “40 ms” and “800 mV”. The game draws “40 MS” and “800 MV”. The docs quote the preview, not the screen.
Position
Hard-coded top-right, margin 5×scale. There is no position field in overlay.toml and no code that could honour one.
Refresh
FPS is the layer’s own median over a present-frametime ring, so it is smooth. Everything else is 1–10 s, straight from the daemon’s engine tick.

03 · The target

Three different things people call “the Steam overlay”

Worth separating before promising any of it. Only one of the three is both valuable here and buildable without reinventing a game client.

What it is What it gives For us
Steam FPS counter A small corner readout with a position choice and a high-contrast background. match and pass
We already show more; we show it worse.
Steam Deck performance overlay Detail levels 1–4, real type, translucent panel, frametime graph, live tuning from the same panel. the actual target
Every number it shows, we already have — plus tier and undervolt.
Shift+Tab overlay A full interactive UI: browser, friends, screenshots, mouse capture inside the game. out of scope
Needs input capture and a client to be part of. Steam-only by nature; we also serve Lutris and Heroic.

So the goal is not a Steam clone. It is: a HUD that looks like it belongs in 2026, showing things only PenguinBurner knows — which tier is active, what the undervolt is doing, when the tier last switched — and reachable without alt-tabbing out of the game.

04 · What is already paid for

The layer is further along than it looks

The reason stage 1 is worth attempting: everything a real renderer needs around the pipeline already exists and has been shipping.

Per-swapchain resources
Image views, a render pass, framebuffers, a command pool and per-image command buffers, fences and semaphores — created, recreated and torn down correctly today.
Present-path integration
One extra queue submit chained into vkQueuePresentKHR through the present’s own wait semaphores, with a fence guard that skips a frame rather than stalling it.
Config and live state
A polled config file, a live on/off override the GUI can flip mid-game, and a telemetry file with 22 fields already parsed in C++.
What is missing
A graphics pipeline, two shader modules, a font atlas and a vertex buffer. That is the whole delta — roughly the last 20% of a HUD renderer.

05 · The plan

Four stages, each shippable alone

What each stage contains. The order below has since been revised — a second read of the draw path showed that layout, type and even the frametime graph all fit the renderer we already have, so the pipeline work moved last and the risk moved with it. The working sequence lives in Overlay Build Order.

S1

A real renderer

risk · medium native only

Replace the clear-rect glyph blitter with a graphics pipeline: two tiny shaders, one instanced quad draw, alpha blending on. The surrounding render pass, command buffers and submit stay exactly as they are.

  • Shaders ship pre-compiled. SPIR-V embedded as a generated header, produced by a committed script — no glslang on a packager’s machine, 32-bit build included.
  • The old path stays as the fallback. If pipeline creation fails for any reason, the layer draws today’s bar instead of nothing. A game that works now cannot stop working.
  • Colour and opacity become expressible the moment blending is on, which is what every later stage spends.

unlockstranslucency · per-metric colour · any screen position · multiple lines · graphs

S2

Typography and layout

risk · low native + config + GUI + docs

The part users actually see. A full-ASCII font with lowercase and punctuation, a panel that can sit in any corner, and detail levels instead of thirteen independent checkboxes.

  • Font: a generated atlas, again from a committed generator. Lowercase and : arrive with it, and the caps mismatch between the preview and the screen disappears.
  • Position, opacity, corner padding as real overlay.toml fields, with matching controls in the Overlay tab.
  • Detail levels 1–4 in the Steam Deck sense — FPS only, FPS plus tier, the current set, everything — with the existing per-item checkboxes kept as the custom level.
  • One layout description, two consumers. The GUI preview and the layer must render from the same rules, or the preview lies again the first time either changes.

fixespreview-vs-screen mismatch · the all-caps readout · the welded corner

S3

What only PenguinBurner can show

risk · low native + daemon

Once quads are cheap, the differentiator against MangoHud is not more numbers — it is the tuning story behind them.

  • Frametime graph with the 1% low and the session min/avg, drawn from the ring buffer the layer already keeps.
  • Tier-change markers on that graph. “Switched to Balanced” sitting where the frametime moved is a thing no other overlay can draw.
  • Threshold colouring — temperature, power ceiling, missed frames — so the panel is scannable rather than read.
  • Optional: sub-second GPU telemetry. The engine loop currently sleeps min(poll, overlay), floored at one second, so a faster HUD speeds the whole daemon loop. It needs its own publisher before it needs a smaller number.

givesthe answer to “why is MangoHud not enough?”

S4

Reach it without leaving the game

risk · low to start CLI + daemon + docs

The missing edge in the diagram, opened the cheap way first: no input capture, no hooks, nothing in the layer.

  • CLI verbs — toggle the HUD, cycle the detail level, cycle the tier for the running game — routed into the daemon the way every other privileged action already is.
  • The user binds them as a desktop shortcut. Works on X11 and Wayland, in fullscreen, with zero new privilege, and we document the KDE and GNOME steps.
  • A short toast in the HUD confirming what changed, so the keypress has an answer on screen.
  • Later, if wanted: daemon-side hotkeys over evdev. Worth saying plainly — a root process reading every input device is keylogger-shaped, and it needs a narrow, auditable design before it is worth the capability.

givesthe Steam Deck feeling: change the tier mid-fight, see it confirmed

06 · Deliberately not doing

Where the line is

×Input capture and an in-game cursor. It means hooking the game’s window and input stack per windowing system, and it is the single largest source of “this overlay broke my game” reports for every project that has tried.
×A browser, friends list or screenshot manager. Those are client features, not overlay features. We do not have a client and do not want one.
×Anything Steam-only. The overlay serves Lutris today and Heroic next; a design that assumes a Steam client would have to be undone twice.
×A second config surface. Detail levels replace checkbox soup; they do not get added on top of it.

07 · Needs a decision

Three calls before code

How far on interactivity?

CLI verbs plus a documented desktop shortcut, or a daemon-side evdev hotkey listener that works without the user configuring anything?

leanShip the CLI route in S4. It is a day of work against a week, and it makes the evdev question answerable with real usage instead of a guess.

Which font technology?

A generated bitmap atlas covering full ASCII keeps the instrument look and adds zero dependencies. A signed-distance-field atlas from an open font scales cleanly to 4K and looks modern at any size.

leanBitmap first — it lands with S2 and already fixes the visible problems. SDF is a self-contained upgrade afterwards if the look still bothers us.

Does S1 land behind a flag?

A new pipeline in the present path of every wrapped game is the one genuinely risky change here.

leanYes — an overlay.toml renderer switch, defaulting to the new path once it has run on a few games, with the old renderer as both the fallback and the escape hatch.

Validation reality: none of this can be checked on the review machine — no NVIDIA GPU, no daemon, no Vulkan game. Everything from stage 1 onwards is a desktop-PC job, and the honest sequencing is: build behind the flag, verify on your hardware, then default it on. The Python side of stages 2 and 4 — config, GUI, CLI, docs, preview parity — is fully testable here.
